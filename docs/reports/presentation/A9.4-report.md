## CACHE ARCHITECTURE
There is still one cache: `PowerPointSlideCache` from A9.3, the only `PowerPointSlideImageProviding` in the app, shared through `AppContainer`. A9.4 changes only what it checks and how it writes.

```
Files/Generated/<document-uuid>/            DocumentService.generatedFilesDirectory (A9.3)
  Slides/                                   the cache
    slide-001.png … slide-NNN.png
    cache.json                              metadata (new)
  Slides-<uuid>.partial/                    only while a render runs (new)
```

Opening a deck works like this:
1. Read the source file's size and modification date.
2. If the cache is valid, open it. That is a cache hit; nothing renders.
3. Otherwise join the render already running for that document. If none is running, start one.
4. Before rendering, check the cache again. Another open may have just finished it.
5. Render into staging.
6. Write `cache.json`.
7. Rename staging to `Slides`.

## CACHE IDENTITY
- **Location:** `DocumentID`, because the folder is `Generated/<uuid>`.
- **Metadata:** `documentID` must equal the document being opened.
- **Source fingerprint:**
  - size;
  - modification date;
  - SHA-256 of the file, hashed in 1 MB chunks.

## CACHE METADATA
`cache.json` is about 300 bytes:

```
rendererVersion, documentID, sourceSize, sourceModified, sourceSHA256,
slideCount, imageFormat ("png"), longestSidePixels (1920), createdAt
```

Nothing in it is used as a path. Image names are made from `slideCount` alone: `slide-001.png` to `slide-NNN.png`.

## CACHE VALIDATION
A cache is opened only when **all** of these hold. Otherwise it is deleted and rendered again.
1. `Slides` resolves, symlinks included, to a folder inside the document's own `Generated/<uuid>`.
2. `cache.json` reads and decodes.
3. The renderer version is current.
4. The document ID matches.
5. The format is png and the longest side is 1920, the same as the current settings.
6. `slideCount` is between 1 and 10,000.
7. The source size matches.
8. If the modification date differs, the SHA-256 must match.
9. The folder holds exactly `slide-001…N.png` and `cache.json`, with no extra or missing file.
10. Every image is a regular file, not a symlink.
11. Image I/O reads every image's header as PNG, with width and height above 0.

## SOURCE CHANGE DETECTION
| Case | Result | Test |
|---|---|---|
| Other size | Rendered again | `aChangedSourceIsRenderedAgain` (3-slide deck replaced by a 1-slide deck → shows 1, never the old 3) |
| Same size, other content | SHA-256 differs → rendered again | `aSourceWithTheSameSizeButOtherContentIsRenderedAgain` (zip timestamps changed) |
| Date changed, same content | SHA-256 matches → cache used | `aTouchedButUnchangedSourceUsesTheCache` |

The SHA-256 is computed once per render, off the main thread. On opening, it is computed only when the date differs.

## RENDERER VERSION
`PowerPointSlideCache.rendererVersion` is now 1. Bumping it makes every older cache render again. Tests cover both an older and a newer version.

## PARTIAL CACHE HANDLING
A cache with fewer or more slides than its metadata, or a missing image, is never opened. It is rendered again in full, so a deck never opens with fewer slides than it has.

Tests: `fewerSlides`, `moreSlides`, `missingImage`, `extraImage`, `missingMetadata`.

## ATOMIC CREATION
- The render goes into `Generated/<uuid>/Slides-<uuid>.partial`.
- `cache.json` is written last.
- One `moveItem` turns the staging folder into `Slides`.
- An interrupted render leaves only a `.partial` folder:
  - it never counts as a cache;
  - the next render removes it (`anUnfinishedRenderIsNeverOpenedAndIsRemoved`).
- No tmp accumulation:
  - The renderer already removes its own `tmp/PowerPointRender-*` folder on success and failure.
  - The cache also removes any that are more than an hour old. That can only happen if the app was killed mid-render. The renderer's timeout is 180 s, so a running render is never touched.

## CONCURRENT OPEN
- **Same deck opened at once:** there is one render, and every open waits for it. The test opens 3 at once; renders = 1 and peak WebViews ≤ 1.
- **Different decks at once:** each has its own folder, metadata and render.
  - The test opens 3, 1 and 4 slides at once.
  - Each manifest names its own document.
  - No deck's images appear in another's.

## LIMITATIONS
- Not tested on a real device or with a real PowerPoint file.
- The SHA-256 runs only when the modification date changed, so a same-size change with an unchanged date would not be detected. The app writes the stored file only at import, so this needs something outside the app to rewrite it.
- The cache grows about 0.5 MB per slide while the document exists, with no size limit. That is the existing policy; nothing aggressive was added.
- **FUTURE IMPROVEMENT, not done, waiting for approval:** skip the image header checks when the folder's file list and dates match the metadata.
  - **Value:** about 0.02 s at 100 slides.
  - **Cost:** small.
  - **Risk:** a corrupt image would then reach the loader, which already rejects it with "unreadable" instead of rendering again.
  - **Dependency:** none.
